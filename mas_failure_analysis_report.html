Evidence-backed findings

  • The best MAS topology beats SAS in 8 of 8 non-finance model/benchmark pairs, but the median best-MAS token cost is 9.0x the SAS baseline.
  • BrowseComp failures include runs where gold or evidence documents were retrieved but final synthesis still missed the answer.
  • StableToolBench failures can be dominated by repeated tool errors; the selected case study records 79 tool failures in one run.
  • Workbench failures expose tool-routing gaps: some runs call only one domain's tools despite ground truth requiring another domain.

Interpretive hypotheses

  • Bounded relay packets reduce cost, but can drop decisive evidence unless packets carry source-backed claims and unresolved issues.
  • Static topology choice is a poor fit: easy deterministic tasks need validators; ambiguous retrieval needs evidence-focused debate; tool failures need early fallback.
  • More discussion helps only when it introduces new evidence or checks a concrete failure condition.

Why MAS Fails

A causal view from the traces

1. Evidence does not guarantee synthesis

BrowseComp shows a gap between retrieval and answer formation. A run can retrieve relevant or gold documents and still converge on a false negative or unrelated entity.

2. Communication compresses both signal and dissent

Topologies pass bounded packets, not full transcripts. This keeps costs manageable, but decisive evidence, uncertainty, or minority objections can be lost before the final judge.

3. Consensus is not correctness

Many incorrect runs stop with consensus_reached or majority_vote. Agreement is a workflow-control signal, not an evaluator signal.

4. Tool errors compound under discussion

When agents independently retry failing tools, discussion can multiply API/cache failures instead of recovering.

5. Some tasks need validators more than agents

PlanCraft failures often involve action grammar, inventory state, and recipe constraints. These are better checked by deterministic validators than by longer debate.

6. Cross-domain workflows need routing guarantees

Workbench failures can omit the required domain tool entirely. More agents do not help if none are forced to cover every required side-effect domain.

Proposed General Solution

Use dynamic MAS rather than fixed topology selection.

Start cheap.Run SAS or only-voting first for deterministic, low-ambiguity tasks.
Detect failure shape.Classify the live run as retrieval gap, tool error, state-action error, low-confidence disagreement, or domain-routing miss.
Spawn specialists on demand.Use LLM-as-tools or agent spawning for bounded subtasks: retrieval verifier, API recovery worker, domain router, or final-answer auditor.
Switch topology by evidence need.Escalate to fully linked or group debate only when agents have conflicting evidence or high-value ambiguity.
Gate rounds on new evidence.Continue discussion only when a round adds new documents, new tool outputs, or a corrected action plan.
Validate before finalization.Run task-specific validators: citation coverage for BrowseComp, action/state validator for PlanCraft, call-set coverage for WorkBench, tool-error dedupe for StableToolBench.
Limitations

What this report does not prove

  • Failure-mode labels are deterministic heuristics over traces, not human adjudication of every run.
  • Case studies are representative examples selected for diagnostic value; they are not exhaustive.
  • Token costs are trace-derived totals from these artifact runs and should not be generalized to other models or prompts without rerunning.
  • Hypotheses about topology switching and dynamic MAS are design recommendations, not experimentally validated interventions in this repository.
